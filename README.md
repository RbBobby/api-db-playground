# Учебный полигон: Swagger → API → PostgreSQL

Небольшой магазин для практики ручного и автоматического тестирования. Создавайте пользователей и заказы в Swagger, затем проверяйте записи, связи таблиц и остатки SQL-запросами.

## Быстрый запуск

Для уже созданной папки на этом компьютере адреса и особенности хранилища указаны в `VERIFICATION.md`; существующий `.env` настроен для неё.

Требуется работающий Docker с Docker Compose. На macOS предварительно запустите Docker Desktop или Colima. Команды ниже выполняются из папки проекта.

```sh
cp -n .env.example .env
docker compose up --build -d --wait
docker compose exec api python -m tools.seed
```

`cp -n` создаёт `.env`, только если файла ещё нет, и сохраняет существующие настройки. Можно обойтись без `.env`: значения по умолчанию совпадают с примером. Основная команда `docker compose up --build` также работает, но остаётся в терминале и показывает логи. Дождитесь готовности API, затем выполните seed из другого терминала.

- Интерфейс: http://localhost:8000/ (в текущей локальной настройке http://localhost:18080/).
- Swagger: http://localhost:8000/docs
- OpenAPI: http://localhost:8000/openapi.json
- Проверка API и базы: http://localhost:8000/health

Если порт занят, измените `API_PORT` или `DB_PORT` в `.env`, затем повторите запуск. Внутренние адреса сервисов останутся `api:8000` и `db:5432`.

Три сервиса: `api`, `db`, `user-simulator`. Эмулятор относится к профилю `simulation` и при обычном запуске выключен. Миграции автоматически выполняются перед стартом API. Данные PostgreSQL хранятся в томе `postgres_data`.

## Первые пять минут

После заполнения пустой базы появятся пользователи с ID 1–3 и товары:

| ID | Товар | Цена | Остаток |
|---|---|---|---|
| 1 | Блокнот | 100.00 | 10 |
| 2 | Ручка | 25.50 | 20 |
| 3 | Рюкзак | 2500.00 | 3 |
| 4 | Кружка | 450.00 | 1 |
| 5 | Календарь | 300.00 | 0 |

1. Откройте Swagger, найдите `POST /orders`, нажмите **Try it out**.
2. Введите запрос и нажмите **Execute**:

```json
{"user_id":1,"items":[{"product_id":1,"quantity":2}]}
```

3. Ожидается `201`, `status: "created"`, `total_amount: "200.00"`. Сохраните `id` заказа.
4. Подключитесь к БД любым способом из следующего раздела и выполните:

```sql
SELECT * FROM orders WHERE id = 1;
SELECT * FROM order_items WHERE order_id = 1;
SELECT id, name, stock FROM products WHERE id = 1;
```

Замените ID заказа, если API вернул другое значение. Появятся один заказ, одна позиция на 2 блокнота по 100.00; остаток товара станет 8.

5. В Swagger вызовите `POST /orders/{id}/cancel`. Статус станет `cancelled`, время отмены заполнится, остаток снова станет 10.

Для JOIN всех четырёх таблиц используйте Q4 из `queries.sql`. Все 12 ручных сценариев находятся в `TEST_CASES.md`.

## Подключение к PostgreSQL

Настройки DBeaver для стандартного `.env`:

| Поле | Значение |
|---|---|
| Драйвер | PostgreSQL |
| Host | localhost |
| Port | 5432 или ваш `DB_PORT` |
| Database | playground |
| Username | playground |
| Password | playground_local |
| Schema | public |

Значения Database/Username/Password соответствуют `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`. После первого создания тома изменение этих переменных не меняет существующие учётные данные PostgreSQL. Учебная роль создаётся образом PostgreSQL и имеет право создавать изолированные тестовые базы.

Через терминал, без установленного локально PostgreSQL:

```sh
docker compose exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

Внутри psql: `\dt` — таблицы, `\q` — выход. Не забудьте `;` в конце SQL-запроса.

Запустить все готовые SQL-проверки (в запросах по умолчанию используется ID 1):

```sh
docker compose exec -T db sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < queries.sql
```

## Заполнение и сброс

```sh
docker compose exec api python -m tools.seed
```

Seed добавляет отсутствующих пользователей по email и товары по имени. Повторный запуск не создаёт дубликатов и не восстанавливает уже потраченные остатки. Если до seed создавались свои записи, ID могут отличаться от учебных примеров.

Для исходных ID и остатков выполните сброс. Он удаляет **все записи магазина**, включая созданные эмулятором, и заново создаёт 3 пользователей и 5 товаров. Остановите эмулятор и дождитесь завершения запросов:

```sh
docker compose --profile simulation stop user-simulator
docker compose exec api python -m tools.reset --yes
```

Сброс выполняется одной транзакцией, миграции остаются. Пропуски в ID после отката не означают частичный заказ: последовательности PostgreSQL не откатываются вместе с транзакцией.

## Эмулятор пользователей

Сначала запустите основной полигон и seed. Затем:

```sh
docker compose --profile simulation run --build --rm user-simulator
```

Или с настройками на один запуск:

```sh
docker compose --profile simulation run --build --rm \
  -e SIM_USERS=8 -e SIM_ACTIONS=20 -e SIM_DELAY=0.1 -e SIM_SEED=123 user-simulator
```

| Переменная | По умолчанию | Назначение |
|---|---|---|
| API_URL | http://api:8000 | Адрес API внутри Compose |
| SIM_USERS | 4 | Параллельные пользователи, 1–100 |
| SIM_ACTIONS | 12 | Число действий на пользователя, 1–100000 |
| SIM_DELAY | 0.2 | Задержка после действия в секундах, 0–60 |
| SIM_SEED | 42 | Seed выбора сценариев |

Каждый пользователь сначала регистрируется с уникальным email, затем выполняет заданное число действий: чтение товаров и заказ, отмена либо некорректный запрос. Одно действие может включать несколько HTTP-запросов. В итоговой сводке считаются именно HTTP-запросы, включая регистрацию. Коды 409 при нехватке товара и 422 для намеренно некорректного запроса считаются ожидаемыми отказами; другие ошибки дают код завершения 1. Код 0 означает отсутствие неожиданных ошибок.

При одинаковом SIM_SEED выбор сценариев воспроизводим, однако порядок конкурентных запросов и результаты покупок могут различаться. Уникальные email также различаются между запусками. Для сравнимых исходных условий используйте reset.

## Конкурентная покупка последнего товара

```sh
docker compose exec -e API_URL=http://api:8000 api python -m tools.race
```

Команда создаёт через HTTP двух пользователей и отдельный товар с остатком 1, одновременно отправляет два заказа, проверяет коды `201/409`, один сохранённый заказ и остаток 0. Выводит ID товара, пользователей и результат. Повторные запуски независимы. Записи остаются в БД для проверки Q8 из `queries.sql` — подставьте выведенный ID товара.

## Автоматические тесты

При запущенном полигоне:

```sh
docker compose exec api python -m tools.run_tests
```

Только конкурентные проверки:

```sh
docker compose exec api python -m tools.run_tests -q -k concurrent
```

Команда создаёт новую PostgreSQL-базу с уникальным именем `playground_test_<uuid>`, применяет настоящие миграции, запускает pytest и удаляет **только эту базу** в конце. Таблицы основного полигона не очищаются. Параллельные запуски используют разные базы. При принудительном уничтожении процесса может остаться тестовая база, имя которой напечатано в начале.

Прямой запуск pytest заблокирован проверкой окружения. Тесты используют FastAPI TestClient для API и отдельные соединения PostgreSQL для проверки результата; конкурентные запросы выполняются в разных потоках с отдельными сессиями. SQLite не используется. Для сквозной проверки через HTTP служит `tools.race`.

Проверяются создание пользователя, уникальность email без учёта регистра, сохранение заказа и цен, сумма нескольких позиций, отказ и откат, валидация, отмена и повторная отмена, конкурентная покупка и конкурентная отмена, повторный seed, health и схема ошибок OpenAPI.

## API и ошибки

| Метод | Путь | Успех |
|---|---|---|
| POST | /users | 201 |
| GET | /users/{id} | 200 |
| POST | /products | 201 |
| GET | /products | 200 |
| GET | /products/{id} | 200 |
| POST | /orders | 201 |
| GET | /orders/{id} | 200 |
| GET | /users/{id}/orders | 200 |
| POST | /orders/{id}/cancel | 200 |
| GET | /health | 200 |

Общий формат ошибки:

```json
{"error":{"code":"insufficient_stock","message":"Недостаточно товара 1","details":[]}}
```

404 — неизвестная сущность; 409 — дублирующийся email или конфликт остатков; 422 — неверные параметры. 503 — недоступная БД; 500 — внутренняя ошибка. Для валидации `details` содержит расположение и описание ошибки. Внутренние SQL-ошибки не отправляются в ответе клиенту.

Имя не должно быть пустым; email приводится к нижнему регистру. Цена положительная, до 10 цифр в целой части и 2 после запятой; stock — целое 0–2147483647. В заказе 1–100 разных товаров, quantity — целое 1–1000000. Неизвестные поля отклоняются. Деньги обрабатываются как Decimal/NUMERIC и сериализуются строками. Для создания товара передавайте цену строкой, например `"25.50"`.

## Как обеспечивается согласованность

Создание заказа и изменение остатков находятся в одной транзакции. Товары блокируются `SELECT ... FOR UPDATE` по возрастанию ID: конкурирующий заказ ждёт, затем проверяет актуальный остаток. При любом отказе транзакция откатывается. При отмене сначала блокируется заказ, затем товары в том же порядке. Это защищает и от двойного возврата при параллельных отменах.

БД содержит внешние ключи, уникальность email и пары заказ–товар, проверки положительных цен/количеств, неотрицательного остатка, допустимого статуса и согласованности времени отмены. Наличие хотя бы одной позиции и соответствие суммы позициям гарантирует API, а SQL Q5 позволяет найти нарушения при прямом ручном редактировании БД.

Справочные материалы: [транзакции SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/session_transaction.html), [обработка ошибок FastAPI](https://fastapi.tiangolo.com/tutorial/handling-errors/).

## Остановка, перезапуск и диагностика

```sh
docker compose ps
docker compose logs --tail=100 api db
docker compose restart api db
docker compose down
```

`down` сохраняет том. После `docker compose up -d --wait` данные останутся. `down -v` удаляет том и все учебные данные; для обычной остановки этот флаг не нужен.

Сервисы доступны только через локальные порты компьютера. Авторизация не реализована: проект предназначен для локального обучения.

## Структура

- `app/` — модели, схемы валидации, API и подключение к БД.
- `alembic/` — явная начальная миграция и конфигурация Alembic.
- `simulator/` — эмулятор, использующий только HTTP.
- `tools/` — seed, reset, изолированный запуск тестов, конкурентный HTTP-сценарий.
- `tests/` — API-тесты с SQL-проверками.
- `TEST_CASES.md`, `queries.sql` — ручная практика.
- `VERIFICATION.md` — результаты фактической проверки при создании проекта.


## Веб-интерфейс

Откройте главную страницу сервиса. Фронт обслуживается API-контейнером; дополнительных сервисов не требуется.

- Каталог: поиск товаров, добавление товара, выбор покупателя, корзина и создание заказа.
- Заказы: состав, сумма, фильтры, отмена и повторная отмена.
- Пользователи: создание покупателя и просмотр его заказов.
- Проверка БД: реальные записи четырёх таблиц, обновляемый снимок PostgreSQL и готовый SQL.
- Практика: проверки нехватки остатка, полного отката и количества 0 с сопоставлением четырёх таблиц до и после. Перед проверкой остановите эмулятор.
- Журнал запросов: нажмите строку, чтобы увидеть отправленный JSON и ответ. Журнал хранится в памяти текущей страницы.

Добавлены GET /users, GET /orders и read-only GET /lab/database. Произвольный SQL из браузера не исполняется. Денежные значения передаются строками, сумма корзины вычисляется без потери точности.

При наличии Node.js фронтенд проверяется командами `npm run check` и `npm test`, без установки npm-зависимостей.
